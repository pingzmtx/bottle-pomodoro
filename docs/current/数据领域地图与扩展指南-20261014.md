# 数据领域地图 · 与「加一个新域」的接入指南

> 2026-10-14 · 写给**未来的你**（以及未来的 AI）
>
> 背景：项目可能从「番茄钟」长成「人生管理系统」，现在这个界面也许只是其中一小部分。
> 那份体检报告担心的事——「改一处坏三处」——**真实数据是：`appData` 48 个域里，
> 29 个是多文件共写的**（settings 11 个文件写、uiPrefs 10 个、tree 6 个…）。
> 所以这份文档不是「把旧的改漂亮」，而是**给未来的新域划好位置、立好规矩**。

## 一、现在的数据层长什么样（实测）

`appData` 有 **48 个一级域**，平铺在一个对象上。按「有多少文件在写它」排（★ = 多文件共写）：

| 域 | owner（改语义先看它） | 写者数 | 这个域是什么 |
|---|---|---|---|
| `settings` | `01c_engine_timer.js` | **11** | 用户设置（计时/难度/主题/通知） |
| `uiPrefs` | `01b_engine_data.js` | **10** | 界面偏好（折叠态/引导已读/皮肤） |
| `tree` | `01d3_engine_tree_shop.js` | 6 | 树养成 / 金币 / 商店经济（金币已收敛到 `coinEarn`/`coinSpend`） |
| `rankSystem` | `01d_engine_features.js` | 6 | 段位（星/下注/晋级） |
| `records` | `01e_engine_ui.js` | 4 | **核心事实表**：专注记录。所有统计/日历/海报/CSV 由它**现算** |
| `habits` | `01eC_ui_todo.js` | 4 | 习惯定义 |
| `todos` | `01eC_ui_todo.js` | 4 | 计划与待办 |
| `immersiveFocus` | `01f_engine_immersive.js` | 4 | 沉浸式冒险 |
| `teamSystem` | `01d4_engine_team.js` | 3 | 组队 |

完整清单（含每个域的所有写者与说明）在 **`src/data_ownership.json`**，随时可查：

```bash

python3 tools/data_ownership.py --why tree    # 某个域的写者明细
python3 tools/impact.py --top                 # 最该小心的枢纽符号
```

## 二、边界机制：`data_ownership.json` + 棘轮门禁

**规则一句话**：每个域声明 `owner`（主写文件）与 `writers`（有权写的文件清单）；
**新增**一个没登记的越界写入 → 一键链直接红。

- 登记文件：`src/data_ownership.json`（48 个域，每个都有 `note` 说明它是什么）
- 门禁：`tools/data_ownership.py`，已挂进 `verify.py` 的 `domain` 段
- **棘轮**：现状写点全部冻结为基线 → **不阻塞你**；只拦以后新增的越界
  （同 `empty_catch_audit.py` 的做法：老债冻结、新债立拦）

**为什么用棘轮而不是一次性收敛**：48 个域、400+ 处写点，
一次全改的风险远大于收益（尤其计时/渲染状态）。**新债立刻拦**才是关键——
否则每加一个域就多一层越界，最后谁也说不清数据归谁。

**数据层例外**：`01b_engine_data.js` 对所有域都有写权（它写的是「建字段 / 迁移 / 默认值」，
不是业务逻辑）——这是加性演进（ADR #8）的必要条件。

## 三、⭐ 加一个新域（比如「人生管理 → 健康」）的接入清单

照着做，不会破坏任何现有东西：

```js
// ① 数据结构：加性字段（老存档没有也能跑）
//    位置：01b_engine_data.js 的迁移段
if (!appData.health) appData.health = { logs: [], target: null, updatedAt: 0 };

// ② 领域登记：src/data_ownership.json 加一条（不登记 = 门禁红）
//    "health": { "owner": "0F_ui_health.js",
//                "writers": ["01b_engine_data.js", "0F_ui_health.js"],
//                "note": "健康域：作息/运动/体重（数据从哪来、给谁用）" }

// ③ 计算逻辑下沉纯函数（可单测、可复用）
//    位置：00_pure_core.js —— 不碰 DOM / 不碰 appData（有 lint 守）
function healthBmi(weightKg, heightM) { … }

// ④ 界面：新建 src/scripts/0F_ui_health.js + src/template/26_view_health.html
//    模板片段要在 src/template/_order.json 登记（否则构建报「未登记片段」）

// ⑤ 跨模块扩展：**不要包装别人的函数**，用现成的注册口
tbOnViewSwitch(function (view) { if (view === 'health') renderHealth(); }, 'after');  // 切页刷新
window.tbOnGridAfterRender(fn);                                                      // 网格渲染后跟进
// 需要"自己变了通知别人"→ 用 window.store.emit('health.changed') / 订阅

// ⑥ 想改别域的行为？先问「这是谁的事」：
//    是它的事 → 给它加一个注册口（如 01e 的 tbOnViewSwitch），别从外面包

// ⑦ 落盘 / 备份 / 导入导出：**自动跟随**（saveData 与备份覆盖整个 appData）
//    只有要「导出成 CSV / 参与统计」时才需要动 00_pure_core 的表格构造

// ⑧ 验证三件套：
//    • tools/tests/unit_pure.js            —— 纯函数边界用例
//    • tools/audit_<域>.py                 —— 运行期真实路径断言（照 audit_coinledger.py 的骨架）
//    • tools/data_ownership.py             —— 域边界（②登记后应自动通过）
```

**这份清单本身就是「企业级」**：新域有位置（①）、有归属（②）、有测试位（⑧）、
有扩展口（⑤）、不需要碰别人的代码（⑥）。

## 四、收敛路线图（按数据排，不是按丑排）

如果你哪天决定回头收拾存量，**按这个顺序**（依据是「写者数 × 未来改动频率」）：

| 优先级 | 域 | 写者 | 为什么排这儿 |
|---|---|---|---|
| 1 | `settings` | 11 个文件 | 写者最多；而且**任何新功能几乎都要加设置项** → 未来一定反复碰 |
| 2 | `tree` | 6 个文件 | 402 处读写；金币已经收敛过一轮，可照同样的手法收 `points`/`decor` 等 |
| 3 | `records` | 4 个文件 | 核心事实表，22 个文件在读它 —— 改结构影响面最广 |
| 4 | `uiPrefs` | 10 个文件 | 写者多但都很浅（布尔开关），收益中等 |
| 5 | 其余 | 1~2 | 已经健康，**不用动** |

**不做的**：48 个域全量重构、把 appData 拆成命名空间对象、
把顶层 let 搬进 AppState —— 收益小、风险大（理由见交付说明 §二）。

## 五、这份机制怎么"随系统一起长大"

| 你可能要做的升级 | 这份机制怎么接 |
|---|---|
| 加一个全新领域（健康/财务/学习） | 按 §三 的 8 步；门禁自动强制边界 |
| 把数据搬到服务端/多端同步 | 每域已有明确 owner + 写者清单 → 迁移时按域切，不用全量重写 |
| 把某个域独立成模块/包 | `data_ownership.json` 的 owner 就是天然的切分线 |
| 换 UI 框架 / 重写界面 | 纯函数层（`00_pure_core`）+ 域边界不动，界面可以整个换掉 |
| 让 AI 来加功能 | 域清单 + 接入清单 + 门禁 = AI 有明确的落点与红线，不用猜 |
