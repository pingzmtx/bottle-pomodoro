# 架构决策记录（ADR）

> 本文件记录**为什么长这样**，而不是长什么样。格式抄自 Super Productivity 的
> `ARCHITECTURE-DECISIONS.md`：每条写清 **决策 / 理由 / 实现 / 关键文件 / 何时重新审视**，
> 并**如实记下被否决的方案与它实际的代价** —— 挖过的坑不写下来，下一个人会再挖一遍。
>
> 代码回链：关键实现处写 `@see ARCHITECTURE-DECISIONS.md #N`。
> 改代码前先搜一次本文，避免「好心办坏事」。

## #1 · 单文件交付，片段为真源

**决策**：产品是**一个 `index.html`**（零依赖、零构建、双击即用、可直接发微信）。
源码拆成 `src/scripts/*.js` + `src/template/*`，由 `tools/build.py` 合并成 `index.html`；
**片段是唯一真源**，`index.html` 是产物（`build.py --check` 逐字节校验，禁止手改）。

**理由**：目标用户是「想在手机/电脑上打开就能用」的个人用户，不是开发者。
任何「先 npm install」的门槛都会劝退一半人；打包器的收益（tree-shaking、HMR）
在一个无第三方依赖的 3 万行项目里几乎为零，而代价（产物不可读、出问题只能查源码映射）是实打实的。

**实现**：`src/manifest.json` 声明 9 个槽位与文件顺序；`src/template.html` 是拼装产物；
`window_whitelist.json` 记录所有挂到 window 的符号（跨文件通信的**显式出口清单**）。

**关键文件**：`tools/build.py`、`src/manifest.json`、`tools/win_whitelist.py`

**何时候重新审视**：文件数破百、或单文件超过 6000 行（`w6_size.py` 已在守着）时，
拆成多文件的收益才会超过「用户拿到手是一堆文件」的代价。

## #2 · 番茄计数只有一个口径

**决策**：完整🍅 = 1、半个🍅 = 0.5，**只有一份权威实现**。

**理由（历史病根）**：曾经 `countFullTomatoes` 只数完整番茄，却被 5 处当成「总番茄数」用，
于是「半个番茄不算」反复出现、每次打补丁又漏一处（2026-10-08 组队冲刺显示 5、自测 6 就是这个）。
人一多就必然漏 —— 这不是靠细心能解决的。

**实现**：`00_pure_core.js` 的 `calcPomos/getPomos` 是唯一实现；
`tools/check_tomato_single_source.py` 挂 `verify.py`：**登记制** —
任何新的番茄取值函数不登记在 `tools/tomato_entries.txt` 就 FAIL；
已删除的重复计数器名出现即 FAIL。

**关键文件**：`00_pure_core.js`、`tools/check_tomato_single_source.py`、`tools/tomato_entries.txt`

**何时重新审视**：口径要变（比如「半个算 0.5 太重，改 0.3」）时 —— 改一处 + 改登记表即可，
这正是当初做单一口径的目的。

## #3 · 统计一律「从记录现算」，不存计数器

**决策**：番茄数、周完成、抽奖额度、段位等**全部由 `appData.records` 现算**，
不存「今天几个番茄」这类累加字段。

**理由**：计数器与记录是两份真相，删日志 / 改类型 / 导入备份后必然对不上。
**代价（真实案例）**：抽奖曾存「已发次数」计数器 —— 补记 + 删除记录就能**无限刷抽奖**
（2026-10-13 排查）。改成「额度由 records 现算，减去 `lotteryUsed`（只增不减）」才堵住。

**实现**：`lotteryQuotaOf / lotteryAvailFrom / computeRoundStats / rangeStatsFrom` 等纯函数；
`addLotteryChance` 保留为空壳（调用点与门禁依赖这个名字存在）。

**关键文件**：`00_pure_core.js`、`01d3_engine_tree_shop.js`（`syncLotteryCount`）

**何时重新审视**：现算在大数据量下变慢时（当前 1 万条记录级别无压力）。
若真要缓存，缓存必须**带失效标记**且可由记录重建 —— 不许变成第二真相。

## #4 · 计时只存绝对时间戳，永不累加

**决策**：番茄钟不与 `setInterval` 的累计次数挂钩，只存 `endAt` / `startTime` 时间戳，
倒计时显示每次 `endAt - Date.now()` 现算。

**理由（实测依据）**：浏览器后台标签页会把计时器统一钳到 1 次/秒，且第一分钟后基本停摆
（实测：`setInterval(100ms)` 在后台 130 秒内只触发 60 次；`requestAnimationFrame` 0 帧）。
靠累加的计时器在切后台后必然走不准。

**实现**：渲染循环与计时彻底解耦；不用 rAF 驱动进度动画；暂停/打断走
`pausedElapsed` / `pausedRemaining` 快照落盘（否则暂停中刷新会丢）。

**关键文件**：`01c_engine_timer.js`

**何时重新审视**：几乎不会 —— 这是物理约束，不是设计偏好。

## #5 · 金币 = 余额 + 流水（账本）

**决策**：`appData.tree.coins` 是余额（**唯一真相**，一切既有读取路径不动）；
`appData.tree.coinLog` 是**加性旁路账本**，记每一笔变动（来源 / 时间 / 类型 / 记账后余额）。
**所有余额变动一律走 `coinEarn` / `coinSpend`，不许直接写 `tr.coins`。**

**理由**：只存余额的货币**无法撤销、无法审计** —— 算错一次就永远说不清「这金币哪来的、
被谁扣的」，误发的奖励也退不回。设计出处：HabitTrove 的 `{ balance, transactions[] }`。

**实现要点**（踩过的坑都在这里）：
- **期初结转**：老存档/导入备份只有余额没有流水 → 按**差额**（余额 − Σ流水）补一笔 `opening`，
  使 `Σ流水 ≡ 余额` 恒成立。判据**必须用差额而不是「账本是否为空」** ——
  记账是「先改余额、后落流水」两步，中间那一刻账本还空着、余额却已变；
  用「空账本」当判据会把这笔入账误当成历史余额，实测把 120 元的入账记成了 240。
- **撤销写反向流水**，不删原条目（原记录 + 撤销记录都留着才可回溯）；已花掉的收入撤不回。
- **超上限压实**：旧笔合并成一条「结转」，不能直接丢（丢了净额，账目就永远差着）。
- **对账**：`coinLedgerCheck()` 随时能算出差额；面板上有出口，不静默。

**关键文件**：`00_pure_core.js`（`coinTxMake/coinLedgerSum/coinTxUndoable`）、
`01d3_engine_tree_shop.js`（`coinEarn/coinSpend/coinUndo/coinLedgerInit`）、
`01e5_ui_tree.js`（明细面板）、`tools/check_coin_single_source.py`（门禁）、
`tools/audit_coinledger.py`（37 条运行期断言）

**何时重新审视**：要给金币加多币种、或引入「金币过期」这类时间维度规则时。

## #6 · 收益走乘数链，参数集中一处

**决策**：金币/成长收益 = `round(base × streakMult × buffMult)`，公式下沉纯函数
（`coinEarnFinal`），参数集中在 `COIN_EARN_TUNING`。

**理由**：写成「一张奖励表 + 一串 if」时，新增一类加成要改计算点、调平衡要翻遍全仓。
设计出处：Level-Up-Life 的 `calculateFinalXP`（难度 × 结果 × 连续性 × Boss 各自可调）。
默认参数与旧实现**数值等价**（连续加成默认关闭），所以是纯结构升级、不动经济平衡。

**实现**：`COIN_EARN_TUNING.DUR_TIERS`（24/48/86 → 1/3/6，取最高档不叠加）；
`DUR_COIN` 降级为派生视图（改了不算数）。

**关键文件**：`00_pure_core.js`（`coinDurBase/coinStreakMult/coinEarnFinal`）、
`01d_engine_features.js`（时长奖励调用点）

**何时重新审视**：真要开连续加成时（把 `STREAK_STEP` 从 0 调成 0.05）——
那是一次经济平衡变更，必须先看商店价格与周兑换上限。

## #7 · 依赖方向单向，跨模块「渲染后跟进」用广播出口

**决策**：分层 `00_*` 纯函数 → `01*` 引擎/UI → `03/05` 增强，**下层不许反向依赖上层**。
需要「A 做完事、B 跟着刷新」时，由**拥有方提供出口**（订阅式广播），而不是 B 去反向调用或包装 A 的内部函数。

**理由（真实翻案）**：曾经用「包装 `window.renderTimeBlockGrid`」让说明行跟着重画 ——
但 01eA 内部有 5 处**本地调用**（切日期/翻周/回今天/折叠展开/日历选日）走函数内部绑定，
包装被完全绕开，说明行就丢在这些路径上。**内部调用绕开一切外部包装**，
所以「渲染方提供广播出口」才是正解（`window.tbOnGridAfterRender`，订阅可叠加、失败不炸主渲染）。

**实现**：`tools/w6_layer.py` 静态检查硬违例；`window_whitelist.json` 管跨文件出口；
订阅方带**重入守卫**（`renderTodos` 自己会调网格渲染，无守卫即无限递归）。

**关键文件**：`tools/w6_layer.py`、`01eA_ui_timeblock.js`（`tbFireAfterRender`）、
`01eC_ui_todo.js`（`_todoListInHook`）

**何时重新审视**：广播订阅超过 5 个、或需要「按条件触发不同订阅者」时（那时才值得上事件总线）。

## #8 · 数据加性演进：新字段 optional + 运行时默认值

**决策**：新增持久化字段一律 optional，读取时兜底默认值；迁移写在 `ensure*` 式**幂等**函数里；
**默认不升 schema 版本号**。

**理由**：升版本保护不了已发布的客户端，还会把落后客户端永久卡住（Super Productivity 决策 #8 同款结论）。
本项目是单文件、无服务端，用户手上有多个历史版本的 `index.html` 与备份文件，
「新代码读旧数据」「旧代码读新数据（多余字段忽略）」两条都必须是安全的。

**实现**：`01b_engine_data.js` 的迁移段是「缺什么补什么」的流水线；
`appData.tree.coinLog` 就是本轮新加字段的样板（老存档无此字段 → 首次访问自动补齐）。

**关键文件**：`01b_engine_data.js`

**何时重新审视**：需要对同一字段做**语义变更**（不是新增）时 —— 那才需要真正的版本迁移。

## #9 · 一致性靠门禁，不靠记性

**决策**：凡是「静态可判、错了会静默出事」的约定，一律做成 `verify.py` 里的一道门禁。
「改完记得跑 X」= 没守。

**理由**：靠记忆维持的约定一定会腐化（这正是 Super Productivity 用 ESLint 强制分层的原因）。
本项目的门禁清单（全部零依赖、<1s、可复现）：

| 门禁 | 守什么 | 出事症状（若无门禁） |
|---|---|---|
| `w6_layer.py` | 分层依赖方向 | 架构悄悄腐化，环依赖 |
| `w6_size.py` | 单文件规模红线 | 一个文件膨胀到没人敢改 |
| `w6_toc.py` | 函数索引与代码同步 | 文档与代码脱节 |
| `id_audit.py` | `getElementById('x')` 的 x 必须存在 | 静态看不错、一跑就 null |
| `check_tomato_single_source.py` | 番茄单一口径 + 常量不写死进文案 | 同一份数据两处显示不同数 |
| `check_coin_single_source.py` | 金币只经入账口变动 + 流水类型登记 | 账目悄悄对不上 |
| `check_modal_unify.py` | 弹窗同构（h3 + 按钮行 + 变体类） | 暗色模式补丁一处一处数着打 |
| `check_case_meta.py` | 用例 tier/owner 齐全 | 用例永远选不中（假绿） |
| `win_whitelist.py` | window 出口清单 | 跨文件暗耦合 |
| `empty_catch_audit.py` | 空 catch 棘轮（只减不增） | 错误被静默吞掉 |

**关键文件**：`tools/verify.py`（挂载点）、上述各工具

**何时重新审视**：某条门禁连续 3 个月零命中（可能规则已失效）或误报率超过真报率时。

## #10 · 错误不吞、不炸：分级上报 + 局部隔离

**决策**：错误分两级 —— **可不致命的**走 `__silent(e, tag)` 上报（带来源标签）；
**必须让用户看见的**用 toast / 弹窗。结算链这类多环节流程里，每个环节**独立 try**：
任一环节异常只跳过自身，不阻断记录保存与后续结算。

**理由**：吞掉错误 = 出故障时零线索；让局部错误炸全局 = 一次小异常毁掉一次专注的结算。
两边都不可接受，所以必须分级。设计参照 Super Productivity 的 `GlobalErrorHandler`：
它**只对第一个未处理错误弹窗**（避免错误风暴淹没用户），且对已知无害错误做白名单抑制（附注释说明原因）。

**实现**：`__silent(e, '01e:hookTbDateEntries')` 带来源标签，便于定位；
结算链（`01d_engine_features.js`）每个副作用独立 try + `warn` 级上报。
错误侧还配了**环形缓冲 + 现场导出**（`06_errRep_错误监控.js`）：
warn 级不进角标、可 `console` 查、可一键导出错误现场（带最近上下文）；
按 tag 节流 500ms，防止 1 秒轮询类的报错刷屏顶掉有效记录。
—— 这条是比「抄来的」更进一步的：Super Productivity 只有 action log，
本项目的错误缓冲直接可导出成一份可发给开发者的现场快照。

**关键文件**：`06_errRep_错误监控.js`（缓冲/节流/导出）、
`01d_engine_features.js`（结算链）、各文件里的 `window.__silent` 调用点

**何时重新审视**：出现「报错确实发生了、但缓冲里没有」时 ——
说明 500ms 节流窗口把有效样本吃掉了（高频不同 fault 撞同一个 tag），
那时该把节流键从 tag 细化到「tag + 错误消息指纹」。

## #11 · 暂停给额度，不禁止

**决策**：单次专注的**打断/暂停累计额度**用完即自动结束该次专注；UI 实时显示剩余额度。

**理由**：暂停是番茄工作法的漏洞（赖在暂停里也算法完成）。解法不是禁止暂停（体验太差），
而是给一个额度。设计出处：番茄ToDo 的「暂停总额度」。
代价提醒：额度**别给太紧**，否则「突然被拦」的挫败感会盖过收益。

**实现**：`timerState.totalInterruptSeconds` 累计 + 额度校验；超额度自动恢复计时并提示。

**关键文件**：`01c_engine_timer.js`（`interruptPomodoro` / `resumeFromInterrupt`）

**何时重新审视**：额度值调整（在设置里可配）—— 属于体验参数，不是架构。

## #12 · 计划外记录块：有名字、无点击

**决策**：时间网格里「没有关联计划」的专注灰块，显示任务名（块内截断 + 悬停完整名），
但**不响应点击**。

**理由**：用户拍板 —— 灰块的价值是「知道那段时间干了啥」，不是入口。
它和日志卡的关系是**数据同源**（都出自 `appData.records`），不需要跳转；
给它加点击行为反而会制造「点了应该有反应」的预期落差。

**关键文件**：`01eA_ui_timeblock.js`（`tbPaperUnplannedHtml`）

**何时重新审视**：用户明确要求「点灰块跳到对应日志」时 —— 那时点击才成为需求而不是噪音。

## #13 · 计时模式用策略表，而不是满地 if

**决策**：番茄钟 / 正计时 / 流式三种计时模式的差异，收进一张 `TIMER_STRATEGIES` 表；
链路只查表（`strategyOfFreeType(ft).countsDown` 这类），**不再到处 `if (freeType === 'flowtime')`**。

**理由**：改造前有 **17 处**模式判定散在计时链路的五个环节（启动 / 暂停 / 继续 / tick / 渲染）里。
后果是：改某个模式的行为要翻遍整条链路（漏一处就「有时对有时错」）；
加第四种模式要在这 17 处各加一个分支；而且**两个分支长成一模一样也没人敢删**
——`finishFreeTimer()` 里就有一处 `if (flowtime) {A} else {A}`，逐字符相同，
是历史上两种模式算法统一后留下的死分支（本轮清掉）。
设计出处：Super Productivity 的 `focus-mode-strategies.ts`（三种专注模式各实现同一接口，
新增模式 = 加一个类 + 工厂注册一行）。

**实现**：`TIMER_STRATEGIES`（pomodoro / stopwatch / flowtime）+ 两个取法
（`strategyOfFreeType` 用于已知自由模式的上下文、`timerStrategy()` 组合判定）+ `isFreeMode()`。
**数据模型一个字没动**（`timerMode` / `freeType` 照旧存储，快照 / 恢复 / 导入导出全不受影响）。

**关键取舍**：这是一次**重构**，硬指标是「行为逐字节等价」——所以配了
`tools/audit_timer_modes.py`（27 条断言，**每条都对应一个被替换的判定点**，
注释里写明原判定，如「旧判定：freeType !== 'flowtime' → 累计显示」）。

**关键文件**：`01c_engine_timer.js`（策略表 + 12 处）、`01g_engine_init.js`（5 处）、
`tools/audit_timer_modes.py`

**何时重新审视**：要加第四种计时模式时（那时才真正吃到本决策的红利：
加一个对象、链路一行不动）；或模式间差异收敛到只剩一两处时（那说明表太薄，可退回去）。

## #14 · 跨模块扩展点用注册式钩子，不各自包装

**决策**：需要「A 做完事，B/C/D 跟着做点什么」时，**由拥有方提供注册口**
（`tbOnViewSwitch(fn, phase)`、`tbOnGridAfterRender(fn)`），各模块注册；
**不再用 `window.X = function(){ ...orig.apply... }` 层层包装。**

**理由（两轮实证）**：
- 第一轮（日程链路）：01eM 包装 `window.renderTimeBlockGrid` 补插说明行 ——
  但 01eA **内部有 5 处本地调用**走函数内部绑定，包装被完全绕开，说明行丢在这些路径上。
- 第二轮（视图切换）：`switchView` 被 **4 个模块各自包装**（01g 侧边栏 / 02 统计图 /
  05 存展开计划 + 折卡回收 / 0B 同步 hash），谁先包谁后包由 `<script>` 顺序决定（隐性依赖），
  加第 5 个得先读懂全部 4 个；而且「切前要做」和「切后要做」混在同一个包装里。

**实现**：`01e_engine_ui.js` 提供 `tbOnViewSwitch(fn, phase)`（phase = before/after），
switchView 拆成 `switchView`（触发钩子）+ `switchViewCore`（正文，逐字未改）。
四个模块改为注册。**钩子按注册顺序执行（= 文件加载顺序），与旧包装的嵌套顺序一致**；
after 钩子在 `finally` 里触发（等价于旧包装「apply 之后无条件执行」）；
钩子抛错只跳过自身，绝不阻断切换。

**关键文件**：`01e_engine_ui.js`、`01g` / `02` / `05` / `0B`（四个注册点）

**何时重新审视**：钩子种类超过 3 种、或需要「按条件只触发部分订阅者」时 ——
那时才值得上通用事件总线；现在两个注册口（视图切换、网格渲染）刚好够用。

## #15 · 数据域边界：每个域声明「谁有权写」，棘轮式只拦新增

**决策**：`appData` 的每个一级域在 `src/data_ownership.json` 登记 `owner`（主写文件）与
`writers`（有权写的文件）；**新增**越界写入由 `tools/data_ownership.py` 拦下（已挂 `verify.py`）。
现状写点**冻结为基线**（棘轮），不要求立刻收敛。

**理由**：实测 48 个域里 **29 个是多文件共写**（settings 11 个文件、uiPrefs 10 个、tree 6 个）——
这就是「改一处坏三处」的确切形态：改一个域的字段语义，要在十几个文件里分清谁写、谁读、
谁的读法依赖旧语义。但**一次收敛 400+ 处写点，风险大于收益**；
真正要紧的是「以后别再长」——所以拦新增、冻结存量。

**为什么这条现在做**：项目可能长成「人生管理系统」，现在这个界面只是其中一部分。
那时会不断加入新域（健康/财务/学习…），如果每个新域都随便写别人的数据，
边界会在第三、第四个域时彻底消失。**先立规矩，再长大。**

**实现**：
- `src/data_ownership.json`：48 个域，每个带 `note`（这个域是什么，写给未来的自己）
- `tools/data_ownership.py`：`--report` 看地图 / `--why <域>` 看写者 / `--baseline` 重建基线
- 数据层 `01b_engine_data.js` 例外（它对所有域有权，写的是建字段/迁移，不是业务逻辑）
- 与 `tools/impact.py` 配套：改前先量化影响面、看管辖归属

**关键取舍**：不做「全量收敛」，也不把 appData 拆成命名空间对象——
前者风险大，后者只是把 `appData.tree` 改叫 `AppState.tree`（可见性一模一样）。
**用机制（登记 + 门禁 + 棘轮）替代大重构**。

**关键文件**：`src/data_ownership.json`、`tools/data_ownership.py`、`tools/impact.py`、
`docs/current/数据领域地图与扩展指南-20261014.md`（含「加一个新域」的 8 步接入清单）

**何时重新审视**：某个域连续被 3 个以上新功能改动时（那时按域做真正的收敛，
路线图见地图文档 §四）；或域数超过 80 个时（该考虑按域拆文件了）。

## #16 · 小工具只有一个实现（补零/取今天/取日期/转义）

**决策**：这类「一行小事」全仓**只许有一份实现**（放在 `00_pure_core.js`，转义在 `01e` 作权威），
其他文件要就调用；有意例外（错误监控自包含）登记理由。由 `tools/check_dup_utils.py` 守（已挂一键链）。

**理由（实测，2026-10-14 用户要求「命名/变量别乱七八糟」时扫出来的）**：
真正的「乱」不是名字丑，而是**同一件小事每个文件各写一份、名字还不一样**：

| 概念 | 改造前 | 分布 |
|---|---|---|
| 补零 | `_p2` / `_pad` / `pad2` / `p2` | 4 份（pure_core / 02 / 03 / 04 / 05） |
| 取今天 | `getTodayStr` / `_todayStr` | 2 份（pure_core / 02 / 03） |
| 时间戳→日期 | `getDateStr` / `_dstr` | 2 份 |
| HTML 转义 | `escapeHtml` / `esc`×3 | 4 份 |

危害不在多几行，而在**改一处漏一处**：哪天要收紧转义规则，得先在 4 个文件里把它们全找出来。

**实现**：删掉 9 份私有实现、调用点改走权威版（共约 40 处），
顺手把 `escName` 改名为 `sanitizeName`（它做的是「转成合法标识符」，不是转义 —— **名字不准也是乱**）。

**为什么错误监控是例外**：`06_errRep` 必须在**别人出错时**还能工作，
不能依赖 `01e` 是否已加载 —— 依赖别人就等于「01e 挂了，错误面板一起挂」。

**关键文件**：`tools/check_dup_utils.py`、`00_pure_core.js`、`02` / `03` / `04` / `05` / `0C`
**何时重新审视**：某类工具出现第 3 处重复时，在 `CONCEPTS` 里加一条（门禁立刻守住）。

## #17 · 质量要可度量、可回归（覆盖率 / 性能 / 无障碍都要有数字 + 门禁）

**决策**：把覆盖率、性能、无障碍这三类「质量」都从「一次性做过」变成「持续守住」——
每一类都要有**可量化的数字**（并冻结为基线）和**自动门禁**（退化即 FAIL），不靠人记、不靠自觉。
三件工具分别挂进 `verify.py` 的 `cov` / `perf` / `a11y` 段。

**理由（三件实测证据）**：

1. **47 个业务规则函数零覆盖**：`00_pure_core.js` 120 个具名函数里只有 73 个被单测覆盖（60.8%），
   未覆盖的全是业务规则载体（`todoOccursOn` 周计划归日、`habitCurrentStreak` 习惯连续天数、
   `ebReview` 艾宾浩斯复习间隔、`normMemo` 备忘录留存、`quadRank` 四象限排序、15 个日程网格几何函数…）。
   这些是纯函数、**改错了不报错、只静默改变业务行为**——最该有回归网的地方反而没网。
2. **性能只有一次性数据**：`tools/bench.py` 能测冷启动/视图切换/统计页渲染，但跑完就没了，
   没有人对比历史，**性能退化无人知**。
3. **`09_a11y_无障碍.js` 写了但没验证生效**：无障碍层交付了，却没有自动验证它「还在、还有效」——
   模板里 6 个翻页符号按钮漏了 `title`，兜底生成的 `aria-label="按钮 ‹"` 让屏读用户听到「按钮 左尖括号」，
    **有名字但听不懂**，静默存在了很久。

**实现**：

- **`tools/coverage.py` + `tools/coverage_baseline.json`**：用 Node 内置 V8 coverage（`NODE_V8_COVERAGE`）
  统计 `00_pure_core.js` 的函数覆盖，**双维度棘轮**——已覆盖函数数不得低于基线、未进入分支块数不得高于基线。
  本轮补 211 条断言（unit 363→574）后，函数覆盖率 **60.8% → 100%**（120/120），剩余未进入分支块 81 处。
  挂 `verify.py` 的 `cov` 段。
- **`tools/perf_gate.py` + `tools/perf_baseline.json`**：把 bench 指标基线化，
  阈值口径 `允许上限 = max(基线 × 1.5, 基线 + 绝对下限)`。
  基线（CPU 降速 6×）：冷启动 201ms / 统计页 8000 条 593ms / 视图切换 plan 12 · log 2 · stats 31 · settings 4 · timer 6 ms。
  挂 `verify.py` 的 `perf` 段（`--e2e` 分支）。
- **`tools/a11y_audit.py`**：10 条断言（静态段 S 模板图标按钮必有可访问名；动态段 D 弹窗角色/可访问名/
  **可访问名不能是无意义兜底**/`aria-live` 常驻区/导航 tab 语义/焦点陷阱 Tab 不逃逸）。
  `--static` 纯静态 <0.3s 挂 `verify.py` 的 `a11y` 段，完整模式需 playwright 手动跑。

**关键取舍**：

- **覆盖率用函数级而非行级**：单文件合并架构下，模块加载会把大量「只声明未调用」的行也算进执行，
  行覆盖率会**严重高估**；函数级（「这个函数到底有没有被测过」）才如实回答
  「承载业务规则的纯函数有没有回归网」。
- **性能阈值用「倍率 + 绝对下限」而非纯倍率**：视图切换 3ms→8ms 是 +167% 但绝对值微不足道，
  纯倍率会误报；小数值用绝对下限兜底，兼顾大数值回归与小数值噪声。
- **棘轮式冻结存量**：覆盖率与性能都先把现状冻结为基线（不要求立刻完美），**只拦新增退化**——
  与 #15 数据域边界同一思路：老债不阻塞、新债立拦。

**关键文件**：`tools/coverage.py` + `tools/coverage_baseline.json`、
`tools/perf_gate.py` + `tools/perf_baseline.json`、`tools/a11y_audit.py`、`tools/verify.py`、
`tools/tests/unit_pure.js`、`docs/current/UI改造记录.md` 的 `R-A11Y-GATE-1 / R-COVERAGE-GATE-1 / R-PERF-GATE-1`

**何时重新审视**：① 分支债 81 处收敛到可控区间后，是否把「未进入分支块」也纳入硬阈值；
② ~~移动兼容门禁化补上后~~ **已于本轮补上**（`rs_viewport.py --check` + 棘轮基线，见 `R-VIEWPORT-GATE-1`）——九维至此全部 9.0+；
③ 性能基线随机器换代明显漂移时，按新环境重跑 `--write` 校准基线（而非放宽阈值）。

## #18 · 防线的边界：外部数据必防、内部构造与死代码可减

**决策**：项目由 AI 长期迭代，历次修改都倾向「加一层保险」，积累出大量过度防御。
划一条**唯一判据——看数据来源**：**外部来的必须防**（localStorage 存档、导入的备份 JSON、
URL/hash 参数、用户输入、老版本字段），这是「加性数据演进」（见 #8）的根基，**一律不动**；
**内部构造的可以信任**（同一函数里刚建的对象/数组、常量表、刚赋值的局部变量），对它们判空/查存在，
通常是过度防御，是减法的对象。

**理由**：

- AI 的默认倾向是「再包一层 try」「再判一次空」，成本几乎为零、心理上安全；但**外部数据与内部构造
  被一视同仁地防**，会让「必要的防线」淹没在噪声里 —— 真出问题时，人分不清哪层是有理由的。
- 减法必须**极保守**：判「多余」不能靠读代码时的感觉，要靠工具事实 + 全仓复核（含动态入口）。

**实现（本轮减脂的口径，可复用）**：

1. **死代码先摸底，别急着删**：`node tools/callgraph_ast.js` 出调用图；`tools/w6_deadcode.py` 出候选。
   ⚠️ `w6_deadcode.py` 按「标识符出现次数」计数，**会把注释里的名字也算进去** →
   对「名字恰好写在自己注释里」的死常量（如旧 `TREE_STAGES`）会漏报。补一遍
   **剥离注释后**的 AST 计数即可补出这批。
2. **每个候选都要全仓复核动态入口**：`grep -rn` **必须覆盖 `tools/`、`src/template*.html`、`index.html`**。
   本项目有「字符串拼 onclick / `window['x']` / 注册表 name / 组件注册名」的传统，
   静态调用图漏报动态引用是常态。**本条救下两个「疑似死代码」**：
   - `timerStrategy()` —— src 内零调用，但 `tools/audit_timer_modes.py` 运行时真的调它；
   - `openLogCalendar()` —— src 内零调用，但 `tools/tests/c33_round_goal_todo.js` 真的调它。
   漏掉这一步就会删掉测试面，门禁直接红。
3. **内层 `try/catch`、`typeof fn === 'function'` 这类「看着冗余」的防御，默认不删**：
   前者是 #10 的落地（每副作用独立 try + 来源 tag），后者在 #7 的跨层软依赖里要用来避免硬违例。
   只有**确认恒真/恒假**（如对模板里已不存在的元素做 `querySelector`）时才删。

**关键取舍**：

- **「删了它，什么行为都不会变」是硬门槛**：每处删除都要能说出这句理由，否则不删。
  本轮实际只删 ~40 行（10 处），其余疑似项全部转「不删清单」——**产出的一半是「哪些看着可疑但其实必要」**。
- **死代码工具只给候选，不给判决**：`w6_deadcode.py` 的 `EXEMPT` 名单（定价锚点 `SKIN_DAYS`、
  分页机制 `_logLimit`、预留状态位等）是**人工复核后有意保留**，不是「忘了删」。
- **不顺手改名/改结构**：`_orig2/_ensure2` 这类历史命名核实后确认全在用，改名是零收益的 churn，不做。

**关键文件**：`tools/callgraph_ast.js`、`tools/w6_deadcode.py`、`src/scripts/*`、
`docs/current/UI改造记录.md` 的 `R-SLIMMING-1`

**何时重新审视**：① 再要减脂时，先看 `R-SLIMMING-1` 的「不删清单」，别重复评估；
② 若某处防御对应的功能被正式下线（如 zen 面板彻底移除），其残留防御才从「不删」转为「可删」；
③ `w6_deadcode.py` 若改为「剥离注释后计数」，可去掉本条里「人工补扫」的那一步。
